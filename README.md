#### Связи 
- Переход формальной синхронной на асинхронную event-driven.

Начальная связь: Рейтинг из найма в бонусы

Шаги:
1. Добавляем новое событие в schema registry
```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {

      "type": "string"

      "const": "updated"
    },

      "type": "string"
    },
    "payload": {
      "type": "object",
      "properties": {
        "task_id": {
          "type": "string",
          "format": "uuid"
        },
        "value": {
          "type": "number"
        }
      },
      "required": [
        "task_id",
        "value"
      ]
    }
  },
  "required": [
    "event_id",
    "event_name",
    "produced_at",
    "payload"
  ]
}
```
2. Добавляем консьюмер, который будет обновлять рейтинг, в сервисе бонусов
3. Пишем продюсер в сервисе найма
4. Выключаем синхронную коммуникацию
5. Чистим код от старой коммуникации
   
- Переход формальной асинхронной event-driven на синхронную.

Начальная связь: Стриминг заданий (created) из заданий в найм. Выбрана pull-model

Шаги:
1. Добавить новый эндпоинт - post `api/v0/tasks` в сервисе заданий. 
2. Переписать бизнес-логику на синхронные вызовы в сервисе найма.
3. Когда заработает новая логика, отключить продюсер со стороны сервиса заданий.
4. Подождать, когда консьюмеры обработают все данные из брокера.
5. Удалить код консьюмера со всех сервисов потребителей
6. Удалить таблицу с данными заданий, которые сервис найма получает от pull-процессинга.
7. Удалить топик из брокера.
8. Почистить оставшееся: метрики, код, таблицы в базе
   
- Переход функциональной асинхронной event-driven на синхронную.

Начальная связь: Задание выполнено успешно из найма в бонусы

1. Сделать http-эндпоинт ( `/tasks-succeeded`)на стороне сервиса бонусов
2. Добавить вызов синхронной связи и выключить отправку событий 
3. Подождать, пока события из брокера не обработаются
4. Убрать код, связанный с асинхронной коммуникацией

#### Cпособы решения проблем вокруг зачисления и списания средств

1. DLQ для всех событий, которые могут повлиять на баланс. Мы не можем терять такие события, так как в этом случае менеджер может потерять/получить деньги. А если есть dlq мы гарантированно не затормозим систему. но и не потеряем данные
2. Retry для отправки событий. Пробуем достучатся до брокера, но если нет, можно в dlq, так как событие например после правильного выполнения задания мы потерять не хотим (которое в бонусы идет), но при этом сделать кандидата учителем хотим.
3. Реализовать at-least-once + идемпотентность при обработке событий, чтобы избежать дублирования. Хранить пару event_id:produced_at в любом удобном сторидже. И в момент получения события проверять.
